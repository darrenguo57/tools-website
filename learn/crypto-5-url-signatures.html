URL Signatures: Preventing Tampering

URL signatures let you create links that are tamper-proof and time-limited, all without maintaining server-side session state. When you click a download link from S3, confirm an email address, or reset a password, a URL signature is verifying that the link was generated by the server and has not been modified. This guide covers how URL signing works, complete implementation in JavaScript and Python, and the security considerations that determine whether your signed URLs actually protect your application.

Why Sign URLs?

Consider a password reset flow. The server sends an email with a link like https://app.com/reset?token=abc123. Without signing, an attacker could modify the token parameter, guessing or brute-forcing values until they find a valid one. They could also reuse the link multiple times or access it after the reset period should have expired.

URL signatures solve all three problems. By signing the URL with HMAC, the server can verify that the link was genuinely generated by the server and that no parameter has been modified. By including an expiration timestamp in the signed data, the server can reject expired links without consulting a database. By including a nonce or one-time-use token, the server can prevent replay attacks.

The advantage of URL signing over server-side session tracking is that it is stateless. The server does not need to store issued tokens in a database. The signature itself is the proof of authenticity. This makes URL signing ideal for email links (where the user clicks from a different context than the browser session), pre-authorized download links, and API endpoint protection where you want to avoid the overhead of a database lookup on every request.

How URL Signing Works

URL signing follows a four-step process: construct a canonical string from the URL components, compute HMAC of that string with a secret key, append the signature to the URL as a query parameter, and verify on the server by recomputing the HMAC.

The canonical string must include all data that should be protected: the path, the query parameters, the expiration time, and any other relevant fields. The exact format is up to the implementer, but it must be deterministic: the same URL components must always produce the same canonical string. A common approach is to concatenate the method, path, sorted query parameters, and expiration:

// Canonical string construction
// Format: METHOD\nPATH\nQUERY_PARAMS_SORTED\nEXPIRES

const method = "GET";
const path = "/api/files/report.pdf";
const params = "version=2&user=alice";  // sorted alphabetically
const expires = "1718380800";

const canonical = [method, path, params, expires].join("\n");
// "GET\n/api/files/report.pdf\nversion=2&user=alice\n1718380800"

The HMAC of this canonical string is computed with a secret key known only to the server. The signature and the expiration are appended to the URL as query parameters: https://app.com/api/files/report.pdf?version=2&user=alice&expires=1718380800&signature=abc.... When the server receives the request, it extracts the parameters, reconstructs the canonical string, recomputes the HMAC, and compares it to the provided signature. If they match and the expiration has not passed, the request is valid.

Implementing URL Signatures

Here is a complete implementation in Node.js that signs and verifies URLs. The signing function builds the canonical string, computes HMAC-SHA256, and returns the signed URL. The verification function extracts the signature, recomputes it, and checks the expiration:

const crypto = require("crypto");
const URL = require("url");

const SECRET = process.env.URL_SIGNING_SECRET;

function signUrl(baseUrl, expiresIn = 3600) {
  const url = new URL(baseUrl);
  const expires = Math.floor(Date.now() / 1000) + expiresIn;
  url.searchParams.set("expires", expires.toString());

  // Build canonical string from path + sorted query params
  const params = new URLSearchParams(url.searchParams);
  const sortedParams = [...params.entries()]
    .sort(([a], [b]) => a.localeCompare(b))
    .map(([k, v]) => `${k}=${v}`)
    .join("&");

  const canonical = `${url.pathname}\n${sortedParams}`;
  const signature = crypto
    .createHmac("sha256", SECRET)
    .update(canonical)
    .digest("hex");

  url.searchParams.set("signature", signature);
  return url.toString();
}

function verifyUrl(requestUrl) {
  const url = new URL(requestUrl);
  const signature = url.searchParams.get("signature");
  const expires = url.searchParams.get("expires");

  if (!signature || !expires) return false;
  if (Date.now() / 1000 > parseInt(expires)) return false;

  // Remove signature from params for verification
  url.searchParams.delete("signature");
  const params = new URLSearchParams(url.searchParams);
  const sortedParams = [...params.entries()]
    .sort(([a], [b]) => a.localeCompare(b))
    .map(([k, v]) => `${k}=${v}`)
    .join("&");

  const canonical = `${url.pathname}\n${sortedParams}`;
  const expected = crypto
    .createHmac("sha256", SECRET)
    .update(canonical)
    .digest("hex");

  // Constant-time comparison
  const a = Buffer.from(signature);
  const b = Buffer.from(expected);
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

In Python, the implementation is similar. The hmac and hashlib modules from the standard library handle the cryptographic operations, and urllib.parse handles URL parsing:

import hmac, hashlib, time
from urllib.parse import urlparse, parse_qs, urlencode, urlencode

SECRET = os.environ["URL_SIGNING_SECRET"]

def sign_url(base_url, expires_in=3600):
    parsed = urlparse(base_url)
    expires = str(int(time.time()) + expires_in)
    params = parse_qs(parsed.query)
    params["expires"] = [expires]
    # Sort params for canonical form
    sorted_params = sorted(
        [(k, v[0]) for k, v in params.items()]
    )
    canonical = f"{parsed.path}\n{urlencode(sorted_params)}"
    signature = hmac.new(
        SECRET.encode(), canonical.encode(), hashlib.sha256
    ).hexdigest()
    params["signature"] = [signature]
    return f"{parsed.scheme}://{parsed.netloc}{parsed.path}?{urlencode(sorted_params)}&signature={signature}"

Pre-signed Download Links

Amazon S3 pre-signed URLs are the most well-known application of URL signing. S3 generates a signed URL that grants temporary access to a private object. The URL includes an expiration time, and the signature covers the bucket, key, expiration, and HTTP method. Anyone with the URL can download the object until the URL expires.

The pattern is powerful because it separates the authorization decision from the download itself. Your application generates the signed URL after verifying that the user is authorized to access the file. The file storage system (S3) verifies the signature and serves the file directly, without your application server being involved in the download. This offloads the bandwidth to the storage service.

When implementing your own pre-signed links, include a scoped access parameter in the signed data. For example, sign file=user123/report.pdf&expires=... rather than just expires=.... This ensures the signature is tied to a specific file, so an attacker cannot reuse the signature to access a different file by changing the path. The scoped parameter prevents signature re-targeting attacks.

Email Verification Links

Email verification is another common use case. When a user registers, the server sends an email with a signed link like https://app.com/verify?email=user@example.com&expires=1718380800&signature=abc.... When the user clicks, the server verifies the signature and marks the email as verified.

The signed data should include the email address and an expiration timestamp (typically 24-48 hours). Including the email prevents an attacker from using one user's verification link to verify a different email address. The expiration ensures that if the email is intercepted, the link is only useful for a limited time.

For one-time-use links, include a nonce (a unique random token) in the signed data and store it in the database with a "used" flag. After the first click, mark the nonce as consumed. This prevents replay attacks where an attacker who captures the email uses the link multiple times. The nonce is the only part that requires server-side state; everything else (expiration, email binding) is handled by the signature itself.

Security Considerations

Use constant-time comparison when verifying signatures. A standard string comparison returns at the first mismatch, leaking timing information about how many bytes of the signature are correct. An attacker can use this to recover the signature byte by byte. Always use crypto.timingSafeEqual() in Node.js or hmac.compare_digest() in Python.

Handle URL encoding carefully in the signature. If the signed canonical string contains URL-encoded values, the verification must use the same encoding. A mismatch between how the signing function encodes parameters and how the verification function decodes them can cause valid signatures to be rejected or, worse, allow alternate encodings that bypass the signature. Normalize the URL encoding before signing and after receiving, so both sides use the same representation.

Key management is critical. The signing key should be long (at least 32 bytes), random, and stored securely (environment variable, key vault, or KMS). Rotate keys periodically and support multiple active keys during rotation. If the key is compromised, all signed URLs become forgeable. Use separate keys for different purposes (email verification, download links, API signing) so that compromise of one key does not affect all URL signing in your system.

Common URL Signing Patterns and Variations

Different systems implement URL signing with slight variations. S3 pre-signed URLs include the access key ID in the URL and use the secret access key to sign a canonical request that includes the HTTP method, bucket, key, and query parameters. The signature is verified by the S3 service using the access key ID to look up the corresponding secret key.

Google Cloud Storage uses a similar approach but supports both V2 and V4 signing algorithms. The V4 signing process creates a signing key by deriving it through multiple HMAC rounds (similar to AWS SigV4), which scopes the key to a specific date and service. This means that even if a signing key is intercepted, it can only be used for a short time window.

For custom implementations, a popular pattern is the signed cookie approach, where the server sets an HTTP-only cookie containing the signed access token rather than embedding it in the URL. This is useful for serving protected static assets: the browser automatically sends the cookie with each request, and the server verifies the signature without the token appearing in the URL or being logged. The trade-off is that cookies are domain-scoped, while signed URLs can be shared across users and systems.

Some systems use asymmetric signing for URLs, where the server signs with a private key and the verification service uses the public key. This is useful when the signing server and verification service are separate and you do not want to share a secret key. The trade-off is performance: RSA or ECDSA signing is slower than HMAC. For high-throughput systems, HMAC is preferred because it is significantly faster. The choice depends on your architecture and trust model.

Frequently Asked Questions

How long should a URL signature be?

An HMAC-SHA256 signature is 64 hex characters (256 bits). This is more than sufficient for security. The signature length does not affect performance, so there is no reason to truncate it. Shorter signatures reduce the security margin, though even 128 bits (32 hex characters) would be practically unforgeable.

Can URL signatures expire?

Yes, and they should. Include an expiration timestamp in the signed data and verify it on the server. The expiration is part of the canonical string, so it cannot be modified without invalidating the signature. This makes signed URLs self-expiring without any server-side state.

What happens if the URL is modified?

Any modification to the signed components (path, query parameters, expiration) invalidates the signature. The server recomputes the HMAC from the received parameters and finds it does not match the provided signature. The request is rejected. This is the core protection that URL signing provides.

Should I include the signature in the URL path or query?

The query string is the standard approach and is easier to implement. It keeps the path clean and works with most routing systems. Some systems put the signature in a header (like AWS), which keeps it out of logs but requires the client to be able to set headers, which is not always possible (e.g., browser-initiated downloads).

How do I handle URL encoding in signatures?

Normalize the URL encoding before signing and after receiving. Decode all parameters, then re-encode them in a consistent way before building the canonical string. This prevents mismatches where the signing function uses one encoding (e.g., %20 for spaces) and the verification function uses another (e.g., +). Always use the same normalization on both sides.
