JSON to YAML: Data Format Migration Guide

JSON and YAML are the two most popular human-readable data serialization formats. JSON is the lingua franca of APIs and web services. YAML is the preferred format for configuration files in DevOps. Converting between them is a common task, but the formats have different capabilities and conventions that create subtle traps. This guide walks through the differences, conversion rules, and the pitfalls that catch developers off guard.

JSON vs YAML: Format Comparison

JSON (JavaScript Object Notation) and YAML (YAML Ain't Markup Language) are both human-readable, text-based data formats. They share a common data model: both support maps (key-value pairs), lists, strings, numbers, booleans, and null values. In fact, YAML 1.2 is a strict superset of JSON, meaning every valid JSON document is also a valid YAML document.

The key syntax difference is that JSON uses structural delimiters like braces {} for objects and brackets [] for arrays, while YAML uses indentation for structure. JSON requires quotes around all keys and string values, while YAML allows unquoted keys and values in many cases. JSON does not support comments; YAML supports comments using the # symbol.

YAML supports additional features that JSON does not: comments, multi-line strings (using | for literal block scalars and > for folded block scalars), anchors and aliases (similar to variable references), and type tags. These features make YAML more expressive but also more complex to parse, which is why JSON remains the standard for data interchange between systems.

When to Use YAML Over JSON

YAML excels as a configuration format. It is the standard for Kubernetes manifests, Docker Compose files, GitHub Actions workflows, CI/CD pipeline definitions, and Ansible playbooks. The indentation-based structure is easier for humans to read and edit than JSON's brace-heavy syntax, and comments allow developers to annotate configuration choices directly in the file.

JSON is the better choice for machine-to-machine communication. APIs return JSON because parsers are ubiquitous and fast, the syntax is unambiguous, and the format has no features that could be accidentally exploited (no code execution, no arbitrary type coercion). If a human does not need to read or edit the data, JSON's simplicity is an advantage.

A practical guideline: if the file is written or edited by humans, use YAML. If the data is generated and consumed by software, use JSON. Configuration files that people maintain in version control benefit from YAML's readability and comments. API responses that programs parse programmatically benefit from JSON's simplicity and universal parser support.

Converting JSON to YAML

Converting JSON to YAML is generally straightforward because YAML's data model is a superset of JSON's. Each JSON object becomes a YAML mapping, each JSON array becomes a YAML sequence, and the values map directly. The main transformations are removing structural delimiters, using indentation instead of braces, and potentially simplifying quoting.

Here is a JSON document and its YAML equivalent:

// JSON
{
  "name": "api-server",
  "version": "2.1.0",
  "dependencies": ["express", "pg", "redis"],
  "config": {
    "port": 3000,
    "debug": true
  }
}

# YAML equivalent
name: api-server
version: 2.1.0
dependencies:
  - express
  - pg
  - redis
config:
  port: 3000
  debug: true

When converting, be aware that YAML's type inference can change the meaning of string values. A JSON string value of "yes" becomes the YAML string yes, but many YAML parsers interpret bare yes as the boolean true. To preserve the string type, quote it explicitly: version: "yes". The same applies to values like no, on, off, true, false, and numbers with leading zeros.

Converting YAML to JSON

Converting YAML to JSON is straightforward in principle since JSON is a subset of YAML. The YAML parser reads the document into its native data model, then a JSON serializer writes it out. However, you lose YAML-specific features during conversion. Comments are dropped, multi-line block scalars become single-line JSON strings with escape sequences, and anchors and aliases are resolved to their referenced values.

The most common issue is type coercion. YAML 1.1 parsers interpret many bare words as booleans or other types. For example, the YAML value on becomes true in JSON, and 07 becomes the octal value 7 (or a string, depending on the parser). This is why many CI/CD tools specify string values explicitly with quotes to avoid type coercion surprises. In Python, the PyYAML library handles conversion:

import yaml, json

# YAML to JSON
with open("config.yaml") as f:
    data = yaml.safe_load(f)
print(json.dumps(data, indent=2))

# JSON to YAML
with open("config.json") as f:
    data = json.load(f)
print(yaml.dump(data, default_flow_style=False))

Using safe_load() is important for security. YAML's full spec supports arbitrary type tags that can execute Python code during deserialization, similar to pickle. The safe_load function restricts parsing to standard YAML types and prevents code execution vulnerabilities.

Common Migration Pitfalls

Type coercion is the number one pitfall when converting between JSON and YAML. YAML 1.1 treats yes, no, on, off, true, false, and their capitalized variants as booleans. A version string like version: 1.0 stays a string, but version: yes becomes the boolean true. This has caused real-world bugs in configuration management, where a version field silently changed type.

Indentation errors are the second most common issue. YAML requires consistent indentation (spaces, not tabs), and mixed indentation causes parse errors. A single tab character in a YAML file that uses spaces elsewhere will produce a confusing error message. Most editors can be configured to use spaces for YAML files automatically, which prevents this class of errors.

Anchors and aliases, YAML's mechanism for reusing content, do not exist in JSON. A YAML file using anchors like &default and aliases like *default will convert to JSON correctly, but the references are expanded (the aliased content is duplicated). If you convert that JSON back to YAML, the anchors are lost. Similarly, multi-line strings using | or > become single-line strings with \n escape sequences when converted to JSON.

Another subtle pitfall involves YAML's flow style versus block style. Flow style uses JSON-like syntax with braces and brackets, allowing compact inline representations: colors: [red, green, blue]. Block style uses indentation: each list item on its own line with a dash. Converting from JSON to YAML may produce either style depending on the converter's configuration. Block style is preferred for human readability, while flow style is useful for short inline values. When round-tripping (JSON to YAML to JSON), the style choice does not affect the data, but it does affect readability and diff friendliness.

Unicode handling also differs between the formats. JSON requires that non-ASCII characters be represented as UTF-8 (or escaped as \uXXXX). YAML is also UTF-8 native, but some YAML parsers have had bugs with BOM (Byte Order Mark) handling at the start of files. When converting, ensure both the input and output use consistent UTF-8 encoding without a BOM, which can cause parsing issues in some tools.

Real-World Migration Example

Consider a Docker Compose configuration that a team initially stored as JSON for programmatic generation but wants to migrate to YAML for readability. Here is the transformation:

# Original JSON (machine-generated)
{
  "services": {
    "web": {
      "image": "nginx:alpine",
      "ports": ["80:8080"],
      "environment": {
        "DEBUG": "true",
        "VERSION": "1.0"
      }
    }
  }
}

# Migrated to YAML (human-edited)
services:
  web:
    image: nginx:alpine
    ports:
      - "80:8080"
    environment:
      DEBUG: "true"    # quoted to prevent bool coercion
      VERSION: "1.0"

Notice that the port mapping 80:8080 is quoted in YAML. Without quotes, some YAML parsers interpret 80:8080 as a mapping with key 80 and value 8080, or as a sexagesimal (base-60) number. Quoting it explicitly preserves the intended string type. This is the kind of subtlety that makes manual conversion error-prone and makes a reliable conversion tool valuable.

Validation and Schema Considerations

Both JSON and YAML benefit from schema validation, which defines the expected structure and types of a document. JSON Schema is the standard for JSON validation: it describes required fields, expected types, value ranges, and structural constraints. A schema validator checks a JSON document against the schema and reports any violations, catching errors early in the data pipeline.

For YAML, the situation is more complex. YAML's flexible type system means the same value can be represented in multiple ways, and different parsers may interpret ambiguous cases differently. Tools like yamllint check YAML syntax and style conventions, but they do not validate the semantic structure of the data. For configuration validation, many teams convert YAML to JSON programmatically and then validate against a JSON Schema, getting the best of both worlds.

When migrating between formats, pay attention to how each format handles edge cases. JSON does not allow trailing commas, while YAML is more permissive. JSON strings must use double quotes; YAML allows single quotes, double quotes, or no quotes depending on the value. YAML's flow style (using JSON-like syntax within a YAML document) can be mixed with block style, creating documents that are partially JSON-like and partially indentation-based. During conversion, these mixed-style documents are normalized to one style.

For CI/CD pipelines and infrastructure-as-code, validation is critical. A malformed Kubernetes manifest can cause deployment failures, and a typo in a Docker Compose file can expose ports unintentionally. Using schema validation on configuration files before deployment catches these errors before they reach production. Many tools like kubectl include built-in validation, and standalone tools like cue and jsonschema validators provide CI/CD integration.

Frequently Asked Questions

Is YAML a superset of JSON?

Yes, since YAML 1.2, every valid JSON document is also a valid YAML document. You can paste JSON into a YAML parser and it will parse correctly. The reverse is not true: YAML has features like comments, anchors, and multi-line strings that JSON does not support.

Does YAML support comments?

Yes, YAML supports comments using the # symbol. Everything from the # to the end of the line is ignored by the parser. JSON does not support comments at all, which is why comments in YAML are lost when converting YAML to JSON.

What are YAML anchors and aliases?

Anchors (&name) and aliases (*name) let you define a value once and reference it elsewhere, similar to variables. This reduces duplication in large configuration files. When converting to JSON, anchors are resolved and the referenced content is duplicated at each alias location.

Why does YAML convert "yes" to true?

YAML 1.1 parsers treat yes, no, on, off, true, false, and their case variants as booleans by default. YAML 1.2 restricted this to only true and false, but many parsers still use the 1.1 rules. To preserve string values, always quote them: version: "yes".

Can all YAML be converted to JSON?

Yes, all YAML can be converted to JSON because JSON's data model is a subset of YAML's. However, YAML-specific features like comments, anchors, multi-line strings, and custom type tags are lost or transformed during conversion. The resulting JSON will contain the same data but without the structural conveniences.
