AES Encryption: How It Works and When to Use It

AES (Advanced Encryption Standard) is the symmetric encryption algorithm used worldwide to protect everything from classified government data to the messages on your phone. This guide covers what AES is, how key sizes affect security, why the choice of encryption mode matters more than most developers realize, and how to implement AES correctly using standard libraries. By the end, you will understand the difference between CBC and GCM, why padding exists, and which mistakes make your encryption trivially breakable.

What is AES Encryption?

AES is a symmetric block cipher, meaning the same key is used for both encryption and decryption, and it operates on fixed-size blocks of data. AES processes data in 128-bit blocks (16 bytes) and supports key sizes of 128, 192, or 256 bits. The algorithm was selected by the U.S. National Institute of Standards and Technology (NIST) in 2001 as the replacement for the aging DES standard, following a multi-year open competition that evaluated 15 candidate algorithms from cryptographers worldwide.

The name "Advanced Encryption Standard" refers to the standard (FIPS PUB 197), while the algorithm itself was originally called Rijndael, after its inventors Joan Daemen and Vincent Rijmen. Rijndael supported block sizes and key sizes in multiples of 32 bits, but the AES standard fixed the block size at 128 bits and restricted key sizes to 128, 192, and 256 bits.

Being symmetric means AES is fast and suitable for encrypting large amounts of data. This contrasts with asymmetric algorithms like RSA, which are mathematically limited and slow. In practice, systems use RSA to exchange or wrap an AES key, then use AES for bulk data encryption. This is called hybrid encryption and is the foundation of TLS, the protocol that secures web traffic.

AES Key Sizes: 128, 192, 256 Bits

AES supports three key sizes: 128 bits, 192 bits, and 256 bits. The number of encryption rounds varies with key size: AES-128 uses 10 rounds, AES-192 uses 12 rounds, and AES-256 uses 14 rounds. More rounds mean more diffusion of the input data, which increases resistance to cryptanalytic attacks.

AES-128 provides 128 bits of security, which means a brute-force attack would need to try approximately 2^128 (about 3.4 x 10^38) key combinations. This is astronomically large and is considered secure against any feasible computing power, including quantum computers, for the foreseeable future. AES-256 raises this to 2^256 combinations, which is effectively unbreakable by brute force.

For most applications, AES-128 is sufficient. AES-256 is recommended for data that needs long-term protection (decades or more) or for compliance with specific security standards like FIPS 140-2. The performance difference is minimal on modern hardware, so many developers default to AES-256 for the extra margin. The weakest link in AES security is never the key size; it is almost always the implementation.

Encryption Modes: CBC vs GCM

AES is a block cipher that processes 16-byte blocks. To encrypt data longer than 16 bytes, you need an encryption mode, which defines how each block relates to the next. The mode you choose has a significant impact on security, and picking the wrong one can make your encryption useless.

ECB (Electronic Codebook) is the simplest mode and the most dangerous. Each block is encrypted independently with the same key. This means identical plaintext blocks produce identical ciphertext blocks, leaking patterns in the data. The classic illustration is encrypting an image in ECB mode: the encrypted output still shows the original image's structure. Never use ECB mode.

CBC (Cipher Block Chaining) XORs each plaintext block with the previous ciphertext block before encryption. This means each block depends on all preceding blocks, hiding patterns. CBC requires an initialization vector (IV), a random 16-byte value prepended to the ciphertext. The IV does not need to be secret but must be unpredictable (random for each encryption). CBC does not provide authentication, so an attacker can modify the ciphertext without detection unless you add a separate MAC (message authentication code).

GCM (Galois/Counter Mode) is the recommended mode for most applications. It provides both encryption and authentication (AEAD - Authenticated Encryption with Associated Data). GCM generates a tag that verifies the ciphertext was not tampered with. If the tag does not match, decryption fails. This prevents a class of attacks where an attacker modifies ciphertext and observes the decryption error patterns. GCM uses a nonce instead of an IV, and the nonce must be unique (but not necessarily random) for each encryption with the same key.

Padding: Why and How

Block ciphers operate on fixed-size blocks. If your plaintext is not a multiple of the block size, you need padding to fill the remaining bytes. The most common padding scheme is PKCS#7, which appends bytes whose value equals the number of padding bytes. If you need 3 bytes of padding, the padding is 0x03 0x03 0x03. If the plaintext is already a multiple of the block size, a full block of padding is added.

PKCS#7 padding is self-describing: the last byte of the decrypted plaintext tells the decryptor how many padding bytes to remove. This eliminates ambiguity about where the data ends and the padding begins. The decryptor must validate the padding (each byte must have the correct value) to prevent padding oracle attacks, where an attacker extracts information from padding validation errors.

Stream modes like CTR and GCM do not require padding because they generate a keystream that is XORed with the plaintext byte-by-byte. The ciphertext is the same length as the plaintext. This is one advantage of GCM over CBC: no padding overhead and no padding oracle attack surface.

Implementing AES in Practice

In the browser, the Web Crypto API provides a native, audited implementation of AES-GCM. The API is asynchronous and returns promises. Here is a complete example of encrypting and decrypting data:

// Generate a random 256-bit key
const key = await crypto.subtle.generateKey(
  { name: "AES-GCM", length: 256 },
  true,
  ["encrypt", "decrypt"]
);

// Encrypt
const iv = crypto.getRandomValues(new Uint8Array(12)); // 96-bit nonce
const ciphertext = await crypto.subtle.encrypt(
  { name: "AES-GCM", iv: iv },
  key,
  new TextEncoder().encode("Secret message")
);

// Decrypt
const plaintext = await crypto.subtle.decrypt(
  { name: "AES-GCM", iv: iv },
  key,
  ciphertext
);
console.log(new TextDecoder().decode(plaintext)); // Secret message

In Python, the cryptography library is the standard choice. When encrypting data from a password, never use the password directly as an AES key. Use a key derivation function like PBKDF2 to derive a key from the password with a salt and many iterations:

from cryptography.hazmat.primitives.ciphers.aead import AESGCM
import os

# Generate or load key
key = AESGCM.generate_key(bit_length=256)
aesgcm = AESGCM(key)

# Encrypt (nonce must be unique per encryption)
nonce = os.urandom(12)
ciphertext = aesgcm.encrypt(nonce, b"Secret message", None)

# Decrypt
plaintext = aesgcm.decrypt(nonce, ciphertext, None)

Both examples use GCM mode, which provides encryption and authentication in a single operation. The nonce (12 bytes for GCM) must be unique for each encryption with the same key. Reusing a nonce with the same key catastrophically breaks GCM security.

Common AES Security Mistakes

Hardcoding encryption keys in source code is the most common mistake. Keys committed to version control are effectively public. Anyone with access to the repository can extract the key and decrypt all data encrypted with it. Keys should be stored in environment variables, a key management service (KMS), or a secrets vault, never in source files.

Using ECB mode is the second most common mistake. Despite being explicitly warned against in every cryptography guide, ECB still appears in production code because some libraries default to it. The result is that identical plaintext blocks produce identical ciphertext, leaking structural information about the data.

Reusing IVs or nonces with the same key is catastrophic. For CBC, a predictable IV enables chosen-plaintext attacks. For GCM, reusing a nonce allows an attacker to recover the authentication key and forge messages. Always generate a fresh random IV or nonce for each encryption operation and store it alongside the ciphertext. The IV/nonce does not need to be secret, but it must be unique.

Using weak key derivation is another common problem. Deriving a key by hashing a password with SHA-256 is not sufficient because it allows fast brute-force attacks. Use PBKDF2 with at least 600,000 iterations, or better, use Argon2, which is designed to be memory-hard and resistant to GPU-based attacks.

Key Management in Production Systems

Key management is the hardest part of encryption in production. The AES algorithm is well-studied and its implementations are audited, but if the key is exposed, all encrypted data is compromised. A robust key management strategy addresses how keys are generated, stored, distributed, rotated, and revoked.

Keys should be generated using a cryptographically secure random number generator. In the browser, crypto.getRandomValues() provides this. In Python, os.urandom() or the secrets module. Never use Math.random() or Python's random module for cryptographic keys, as these are predictable and designed for statistical randomness, not security.

For storage, use a dedicated key management service (KMS) rather than storing keys in application code, configuration files, or environment variables directly. AWS KMS, Google Cloud KMS, and Azure Key Vault provide hardware-backed key storage with audit logging and access controls. The application calls the KMS API to encrypt and decrypt data, and the key never leaves the KMS. For simpler setups, tools like HashiCorp Vault provide a self-hosted alternative.

Key rotation is essential for long-term security. If a key is compromised, you need the ability to switch to a new key quickly. Design your system to support multiple active keys simultaneously: each encrypted record stores a key identifier alongside the ciphertext, so the system can decrypt old records with the old key while new records use the new key. Encrypt data under the new key during reads (re-encryption on access) or migrate records in the background.

Frequently Asked Questions

Is AES-256 unbreakable?

No encryption is truly unbreakable, but AES-256 is considered practically unbreakable by brute force. A brute-force attack would need to try 2^256 key combinations, which is more than the number of atoms in the observable universe. The realistic threats to AES are implementation flaws, side-channel attacks, and key management failures, not the algorithm itself.

What's the difference between AES-128 and AES-256?

The key size and the number of encryption rounds. AES-128 uses a 128-bit key with 10 rounds; AES-256 uses a 256-bit key with 14 rounds. AES-256 provides more security margin but is slightly slower. For most applications, AES-128 is sufficient. Choose AES-256 for long-term data protection or compliance requirements.

Can I use the same key for all encryptions?

You can reuse a key, but you must never reuse an IV or nonce with the same key. Generate a fresh random IV (for CBC) or nonce (for GCM) for each encryption operation. The key can stay the same; the IV/nonce must change every time.

What is an IV and why is it needed?

An initialization vector (IV) is a random value that ensures the same plaintext encrypted with the same key produces different ciphertext each time. Without an IV, identical messages would produce identical ciphertext, leaking information. The IV does not need to be secret but must be unpredictable (for CBC) or unique (for GCM).

Is AES encryption or hashing?

AES is encryption, which is reversible with the correct key. Hashing is one-way and irreversible. AES lets you recover the original data; hashing does not. Use AES when you need to read the data back later. Use hashing for passwords and integrity checks where you never need to recover the original.
