HTML Entities: When and How to Use Them

HTML entities let you display characters that would otherwise be interpreted as HTML markup, or characters that cannot be typed on a standard keyboard. They are also your first line of defense against cross-site scripting (XSS) attacks. This guide covers the three types of entities, when each is necessary, how entities prevent XSS, and how modern frameworks have changed the landscape.

What Are HTML Entities?

HTML entities are sequences of characters that represent a single character in an HTML document. They always begin with an ampersand (&) and end with a semicolon (;). There are three types: named entities, decimal numeric entities, and hexadecimal numeric entities.

Named entities use a human-readable name. For example, &lt; represents the less-than sign, &gt; represents the greater-than sign, and &amp; represents the ampersand itself. The HTML specification defines a fixed set of named entities, many of which correspond to characters that would otherwise conflict with HTML syntax.

Numeric entities use the character's Unicode code point. Decimal entities look like &#38; for the ampersand (decimal 38). Hexadecimal entities look like &#x26; (hexadecimal 26). Numeric entities can represent any Unicode character, including those without named entity equivalents. This makes them useful for characters from other writing systems, mathematical symbols, and emoji.

Why HTML Entities Matter

HTML has reserved characters that serve as syntax delimiters. The less-than sign (<) starts a tag, the greater-than sign (>) ends a tag, the ampersand (&) starts an entity reference, and the quotation mark (") delimits attribute values. If you need to display these characters literally in your content, you must use their entity forms.

Consider displaying a code example that contains HTML. If you write <div> directly in your HTML document, the browser interprets it as a real div element rather than displaying the text. By using &lt;div&gt;, the browser renders the literal text <div> on the page. This is why every syntax highlighter or code display tool must escape HTML content.

Beyond reserved characters, entities are used for characters that are difficult to type or that may not render correctly in all contexts. The non-breaking space (&nbsp;) prevents line breaks between words, the copyright sign (&copy;) and the trademark sign (&trade;) provide commonly needed symbols, and entities like &mdash; and &hellip; provide typographic characters not available on standard keyboards.

XSS Prevention with HTML Entities

Cross-site scripting (XSS) occurs when user-supplied data is placed into an HTML document without proper escaping. An attacker can inject <script> tags, event handlers, or other HTML that executes in the victim's browser. The primary defense against XSS is output encoding: converting dangerous characters to their entity equivalents before writing them to the page.

When you escape user input for insertion into HTML text content, you must encode at least three characters: <, >, and &. When inserting into an HTML attribute value, you must also encode the quote character used as the attribute delimiter (either " or '). Here is a JavaScript function that performs HTML escaping:

function escapeHtml(str) {
  return str
    .replace(/&/g, "&")
    .replace(//g, ">")
    .replace(/"/g, """)
    .replace(/'/g, "'");
}

// Safe to insert into HTML:
const userInput = '<script>alert("xss")</script>';
element.innerHTML = escapeHtml(userInput);

The ampersand must be escaped first, before the other replacements. If you escape the less-than sign first, the & in the resulting &lt; would be re-escaped to &amp;lt;, creating a double-encoding bug. Modern frameworks like React, Vue, and Angular automatically escape content by default. In React, content inside JSX curly braces is auto-escaped; using dangerouslySetInnerHTML bypasses this protection and should be avoided unless you have a specific reason and properly sanitize the input.

HTML Entities in Different Contexts

The set of characters that need escaping depends on where in the HTML document the data is placed. In HTML text content (between tags), you need to escape <, >, and &. In attribute values, you additionally need to escape the quote character delimiting the attribute.

Inside JavaScript strings embedded in HTML, the escaping rules change. You need to escape the string delimiter, and you must prevent the string from being terminated early by user input containing the same quote. In CSS context, different characters need escaping. This is why context-aware escaping is critical: applying text-content escaping to data going into a JavaScript context leaves the data vulnerable.

<!-- Text content: escape < > & -->
<p>User wrote: &lt;hello&gt;</p>

<!-- Attribute: also escape quotes -->
<input value="User typed: &quot;test&quot;">

<!-- JavaScript string: different escaping -->
<script>
  var msg = "User said: \\"hello\\"";
</script>

URLs inside attributes require additional URL encoding on top of HTML entity encoding. The href attribute of an anchor tag, for example, needs URL encoding for the URL components and HTML entity encoding for the quote characters.

Event handler attributes like onclick present a particularly dangerous context. The attribute value is both an HTML attribute (needing HTML entity encoding) and JavaScript code (needing JavaScript string escaping). Simply HTML-escaping the value is not sufficient if the data is used as a string literal in the JavaScript code, because JavaScript has its own escaping rules. The safest approach is to avoid inline event handlers entirely and use addEventListener with data stored in data- attributes, which keeps user data out of executable contexts.

CSS context (inside style attributes or <style> blocks) has yet another set of escaping requirements. Characters like parentheses, semicolons, and curly braces have special meaning in CSS and must be escaped if they appear in user-controlled values. The CSS \ escape sequence allows any character to be represented by its hex code. In practice, the safest approach is to avoid injecting user data into CSS entirely, and instead use CSS custom properties (variables) set via JavaScript's style.setProperty() method, which handles escaping automatically.

Modern Alternatives and Best Practices

With UTF-8 now the universal standard for web documents, most special characters can be typed or pasted directly into HTML without entities. You no longer need &eacute; for the letter e-acute; you can simply type it directly. The characters that still require entities are the reserved HTML characters (<, >, &, ") and a few structural ones like the non-breaking space.

Modern DOM APIs provide safer alternatives to manual escaping. The textContent property sets the text content of an element and automatically handles all escaping. Unlike innerHTML, it never interprets the input as HTML, making it inherently safe against XSS:

// Safe: textContent never interprets input as HTML
element.textContent = userInput;

// Unsafe: innerHTML interprets input as HTML
element.innerHTML = userInput; // XSS vulnerability!

When you need to set HTML (not just text), use a sanitization library like DOMPurify to strip dangerous tags and attributes. Frameworks like React, Angular, and Vue escape text by default and provide explicit, opt-in mechanisms for rendering raw HTML, which makes the safe path the default and the dangerous path visible in code review.

Server-Side Template Escaping

Server-side templating engines handle HTML escaping differently, and understanding your template engine's default behavior is critical for preventing XSS. Jinja2 (used by Django and Flask) auto-escapes variables by default, converting <, >, &, and quotes to their entity forms. To output raw HTML, you must explicitly use the safe filter: {{ user_input|safe }}. This opt-out approach makes the dangerous path visible and intentional.

In EJS (Node.js), <%= %> tags escape output automatically, while <%- %> outputs unescaped HTML. Handlebars uses triple-braces {{{ }}} for raw output, and Go's html/template package performs context-aware escaping automatically, choosing the appropriate escaping strategy based on whether the value is placed in HTML text, an attribute, a URL, or JavaScript. This context-aware approach is the most robust because it accounts for the different escaping rules in different HTML contexts without requiring the developer to remember which function to call.

Character Encoding and Document Types

The relationship between HTML entities and character encoding (charset) is a source of confusion. The character encoding declared in your HTML document's charset meta tag or HTTP Content-Type header determines how bytes are interpreted as characters. UTF-8 is the universal standard, capable of representing all Unicode characters directly.

When your document is declared as UTF-8 (<meta charset="UTF-8">), the browser can display any Unicode character directly in the source without entities. The letter e-acute can be typed as the literal character in the source file, and the browser will render it correctly. This is why modern development rarely uses named entities for anything other than the reserved HTML characters.

However, entities remain necessary even with UTF-8 for characters that would conflict with HTML syntax. If you need to display the text <script> on your page, you must use &lt;script&gt; regardless of the character encoding. The browser's HTML parser always interprets < as the start of a tag before it considers character encoding. This is why output encoding for XSS prevention is independent of the document's character encoding.

Another consideration is the HTML version. HTML5 added several named entities that were not available in HTML4. The &apos; entity for the apostrophe is available in HTML5 and XML but not in HTML4 strict. For maximum compatibility across all parsers, use the numeric form &#39; for the single quote. This works in all HTML versions, all XML parsers, and all browsers.

Frequently Asked Questions

Do I need entities if I use UTF-8?

For most special characters like accented letters or emoji, no. UTF-8 lets you type them directly. You still need entities for HTML reserved characters (<, >, &) because they have structural meaning in HTML syntax. Without entities, the browser would interpret them as markup.

What's the difference between &nbsp; and a regular space?

A regular space allows line breaks, so the browser may wrap text at that point. The &nbsp; entity is a non-breaking space that prevents line breaks between adjacent words. It is also a "hard" space that the browser will not collapse with adjacent whitespace, unlike regular spaces which may collapse.

How do entities prevent XSS?

By converting < to &lt; and > to &gt;, any HTML tags in user input are rendered as visible text instead of being parsed as real elements. A script tag becomes harmless text that displays on the page rather than executing.

Should I encode all special characters?

No. Encoding everything works but produces unreadable source code. Encode only the characters that are reserved in your context: <, >, and & for text content, plus quotes for attribute values. Modern frameworks handle this automatically.

What's the difference between named and numeric entities?

Named entities like &lt; use a readable name from a fixed set defined by the HTML specification. Numeric entities like &#60; use the Unicode code point directly. Numeric entities can represent any Unicode character, while named entities cover only a predefined subset. Both produce the same character when rendered.
