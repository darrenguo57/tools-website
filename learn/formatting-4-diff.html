Code Comparison: Diff Tools Explained

Every pull request, every merge conflict, and every bug bisect depends on one concept: the diff. Diff tools compute what changed between two versions of a file and present it in a form humans can review. This guide explains how diffs work, the algorithms behind them, how to read unified diff output, and how modern semantic diffing goes beyond plain text comparison.

What is a Diff?

A diff is a representation of the differences between two sets of text, traditionally an original file and a modified one. Rather than storing two complete copies, a diff records only the lines that were added, removed, or changed, plus enough surrounding context to locate them. This compactness made diffs essential when storage and bandwidth were scarce, and it remains useful for review because the eye is drawn to what changed.

The most common representation is the unified diff format. It groups consecutive changes into hunks, each preceded by a header that gives the file name and the line ranges affected. Inside a hunk, lines starting with a plus sign are additions, lines starting with a minus sign are deletions, and lines starting with a space are context, shown to anchor the change but unchanged themselves.

@@ -10,7 +10,8 @@
 function greet(name) {
-  console.log("Hello, " + name);
+  if (!name) name = "world";
+  console.log(`Hello, ${name}!`);
 }
-
+ 
 module.exports = greet;

The numbers in the hunk header (-10,7 +10,8) mean "starting at line 10 in the old file, 7 lines; starting at line 10 in the new file, 8 lines." Context lines are usually configurable; three lines of context is the default in Git, enough to show the surrounding function without flooding the output. Understanding this format is the foundation for reading every diff a version control system produces.

Some diff tools offer word-level or character-level granularity rather than line-level. A word diff highlights individual changed words within a line, which is more precise when a sentence is edited rather than a whole line replaced. This is especially valuable for documentation and prose, where a line may contain a paragraph and a line-level diff obscures the exact word that changed. Most modern review UIs toggle between line and word modes, and character-level diffs help with minified or single-line files where everything is on one line.

Diff Algorithms: LCS and Beyond

At its core, a diff is the solution to a classic computer science problem: find the Longest Common Subsequence (LCS) shared by two sequences. Lines that appear in the LCS are treated as unchanged context; everything else is an insertion or deletion. The dynamic programming solution to LCS runs in quadratic time relative to the number of lines, which is acceptable for typical source files but can be slow on very large inputs.

The Myers algorithm, used by Git by default, improves on naive LCS by finding a shortest edit script, the minimum set of insertions and deletions to transform one file into the other. It works on a graph of possible edit positions and searches for the shortest path, producing minimal, readable diffs that tend to align well with how developers think about changes. Myers is fast in practice because most real edits are localized, so the search rarely explores the whole space.

Other algorithms suit different cases. Patience diff anchors on unique lines that appear in both files, which produces more stable diffs when a function is moved or reordered. Histogram diff (the default in Eclipse and JGit) refines patience by using the rarest lines as anchors, often yielding the most human-intuitive output for refactors. The choice of algorithm rarely changes correctness, but it changes which lines the tool flags as moved versus deleted-and-readded, which directly affects review readability.

Understanding Diff Output

Reading a unified diff efficiently is a learned skill. Start with the file header, which tells you which file changed and whether it is a new file, a deletion, or a modification. Then scan the hunk headers to see how many regions changed and roughly where. Within each hunk, the minus lines show what was removed and the plus lines show what replaced them; pairing them mentally reconstructs the edit.

Watch for changes that look large but are semantically trivial. Reformatting code, changing indentation, or swapping line endings can produce a diff that touches every line, hiding the one real logic change. This is why teams enforce formatting before commit, so reviewers see meaningful diffs. Also watch for hunks where a block of lines is deleted and an identical block added a few lines later, which usually signals a move that the text diff did not detect. Move detection, available in Git with -M, rewrites these as moves for cleaner output.

Using Diff for Code Review

In a pull request, the diff is the primary artifact a reviewer reads. A good review focuses on the diff, not the whole file, because the changes represent the decision under evaluation. Read each hunk and ask: does this change do what the PR description claims, does it introduce a regression, and does it match the patterns in the surrounding code? The context lines answer the third question, showing the conventions the change must fit.

Diffs also surface regressions during debugging. When a test starts failing, comparing the current code to the last known-good commit reveals exactly what changed. git bisect automates this by binary-searching commits and running a test at each step, narrowing the culprit commit quickly. Without precise diffs, bisect would be impossible, because it relies on comparing states to determine which change introduced the bug.

For reviewers, the diff is a communication tool. Comments attach to specific lines, threading discussion around the exact change. When you write a change, aim for a diff that tells a story: small, focused, with a commit message that explains the why. A reviewer should understand the intent from the diff and message together, without spelunking through the full history. Diffs that mix refactoring, new features, and formatting in one PR are hard to review because the signal is buried in noise.

Beyond Text: Semantic Diffs

A text diff treats code as lines of strings, which breaks down when a change is structurally significant but textually minor. Renaming a variable used in 50 places produces a 50-line diff, but semantically it is one edit. Reordering two independent functions creates a large diff that is logically a no-op. Semantic diffs address this by comparing the abstract syntax tree (AST) of the code rather than its lines.

AST-based diffing parses both versions into a tree of language constructs and matches nodes by structure and content. A rename becomes a single change to the declaration, propagated to references. A moved block shows as a move, not a delete-plus-add. Tools like Difftastic and the tree-sitter-based differ in many modern editors produce these structural diffs, which are dramatically easier to review for large refactors. Some language servers even offer rename-aware diffs inside the IDE.

Semantic diffs are not yet universal because they require a parser for every language and do not translate to the line-based patch format that version control relies on. But as tools mature, they are becoming the default for review UIs, where readability matters more than patch compatibility. Expect the line-based unified diff to persist for storage while richer views dominate the review experience.

Diff Tools in Practice

Git is the dominant source of diffs in modern workflows. git diff shows unstaged changes, git diff --staged shows staged changes, and git log -p shows the diffs in history. IDEs like VS Code and JetBrains render these diffs side-by-side with syntax highlighting and inline actions to stage or revert hunks. For a quick comparison of two arbitrary snippets without a repository, an online diff tool pastes text on both sides and returns a highlighted diff instantly.

For merge conflicts, three-way diff tools are essential. A three-way diff compares the common ancestor (the merge base) with each branch's version, showing what each side changed relative to the base. Tools like Meld, Beyond Compare, and KDiff3 present this as three panes, helping you resolve conflicts by understanding both sides rather than guessing. Configuring Git with a merge tool (git config merge.tool) integrates these into the conflict resolution workflow.

Merge Strategies and Conflict Resolution

When two branches diverge, a merge must reconcile their changes. A fast-forward merge simply moves the branch pointer when one side has no new commits, requiring no diff at all. A three-way merge is the general case: the tool finds the common ancestor, computes what each branch changed relative to it, and combines non-overlapping changes automatically. Conflicts arise only when both branches modify the same lines differently, which is where the diff becomes a tool for human judgment.

A conflict marker in a file shows the three sides, the ancestor, the current branch (HEAD or "ours"), and the incoming branch ("theirs"), separated by angle brackets. Resolving the conflict means reading each side's intent and writing the correct merged result. A three-way diff tool, which displays all three versions side by side, makes this far easier than reading raw conflict markers, because you see what changed from the base on each side rather than just the two final states.

To minimize conflicts, keep branches short-lived and rebase frequently onto the target branch, so the common ancestor stays close to the tip. When conflicts recur in the same files, it signals that two teams are editing overlapping code without coordination, which is a process problem no merge tool can fix. The rebase strategy, which replays your commits on top of the target, produces a linear history and avoids merge commits, but it rewrites history so it should never be used on shared branches. Choose merge or rebase per project convention and apply it consistently.

Frequently Asked Questions

What's the difference between diff and patch?

A diff describes what changed between two files; a patch is a file containing that diff plus instructions for applying it to the original. diff generates the comparison, patch consumes it and modifies files. In Git, git apply and git format-patch bundle these together.

How does Git compute diffs?

Git uses the Myers algorithm by default to find the shortest edit script between the two file versions. You can switch algorithms with git diff --patience or --histogram for diffs that anchor on unique or rare lines, which often reads better for refactors.

What is a three-way merge?

A three-way merge compares two branches against their common ancestor. By knowing what each side changed relative to the base, the tool can auto-merge non-overlapping changes and highlight only true conflicts, where both sides modified the same lines differently.

Can diff tools compare binary files?

Text diffs do not work on binaries, but specialized tools can. Git can show whether a binary file changed and use external drivers (configured via .gitattributes) for formats like images or documents. Tools like ImageMagick can visually diff images pixel by pixel.

What's a unified diff?

A unified diff is the standard format that shows both old and new content in one view. It uses hunks with headers listing line ranges, plus signs for additions, minus signs for deletions, and leading spaces for context lines. Git, patch, and most code review tools use this format.
