Password Generation and Security Best Practices

Passwords remain the most common authentication mechanism, and weak password practices are the leading cause of data breaches. This guide covers what makes a password secure, how to measure strength using entropy, the attack vectors passwords must resist, and the correct way to generate and store them. Whether you are building an authentication system or just protecting your own accounts, these principles apply.

What Makes a Password Secure?

A secure password resists every feasible attack within a practical time frame. Two factors determine that resistance: length and randomness. Length matters because each additional character multiplies the search space an attacker must enumerate. Randomness matters because predictable patterns, common words, keyboard sequences, and personal information let attackers skip vast portions of the search space and guess the password far faster than brute force would require.

The old advice to require a mix of uppercase, lowercase, digits, and symbols sounds rigorous but often backfires. Faced with complexity rules, users create passwords like "Password1!" that satisfy the rules but are trivially guessable. NIST revised its guidelines in 2017 to recommend against mandatory composition rules, instead favoring length requirements and checking passwords against known breach lists. A 20-character passphrase of random words like "correct-horse-battery-staple" is stronger than most 8-character "complex" passwords and easier to remember.

The practical takeaway: prioritize length over complexity. A 16-character password drawn from a large character set has enough entropy to resist offline cracking for centuries with current hardware. A unique password for every account prevents a breach at one service from compromising others. Password managers make both achievable because they generate and store high-entropy passwords that no human needs to remember.

Another dimension of password security is rate limiting on the server side. Even a moderate-strength password is safe if the authentication system limits login attempts. A system that locks an account after five failed attempts renders brute force online attacks impractical. The real danger is offline cracking: when an attacker steals the password database, they can try billions of guesses per second against the hashes with no rate limit. This is why the hashing algorithm matters as much as the password itself, a topic covered later in this guide.

Password Entropy Explained

Entropy measures the unpredictability of a password in bits. Each bit doubles the search space: a 1-bit password has 2 possibilities, 10 bits has 1,024, 40 bits has about one trillion. Entropy is calculated as the base-2 logarithm of the number of possible passwords: H = log2(N^L), where N is the character set size and L is the password length. Simplified, that is H = L * log2(N).

// Calculate password entropy
function calculateEntropy(password) {
  let charsetSize = 0;
  if (/[a-z]/.test(password)) charsetSize += 26;
  if (/[A-Z]/.test(password)) charsetSize += 26;
  if (/[0-9]/.test(password)) charsetSize += 10;
  if (/[^a-zA-Z0-9]/.test(password)) charsetSize += 33;  // Common symbols

  const entropy = password.length * Math.log2(charsetSize);
  return Math.round(entropy * 10) / 10;
}

// Strength benchmarks:
//   < 28 bits  = Very weak (instant crack)
//   28-35 bits = Weak (minutes to hours)
//   36-59 bits = Reasonable (days to years)
//   60-127 bits = Strong (centuries)
//   128+ bits  = Cryptographically strong (heat death of the universe)

console.log(calculateEntropy('password'));        // ~37 bits (but NOT random — dictionary attackable)
console.log(calculateEntropy('Tr0ub4dour&3'));    // ~69 bits (but predictable leet patterns reduce effective entropy)
console.log(calculateEntropy('correct-horse-battery-staple')); // ~91 bits
console.log(calculateEntropy('xK9#mP2$vQ7!nL4@')); // ~104 bits

Note the caveat: entropy formulas assume uniform random selection. A password like "password" calculates to 37 bits, but dictionary attacks crack it in milliseconds because it is not random. Effective entropy depends on how the password was generated, not just its character composition. This is why generated passwords are stronger than human-chosen ones of the same length: a generator produces uniform randomness, while humans introduce patterns attackers exploit.

Types of Password Attacks

Understanding attacks clarifies why certain password practices matter. Brute force tries every possible combination in order. A 10-character password of mixed case and digits has about 59 bits of entropy, meaning 2^59 (about 576 quadrillion) combinations. Modern GPUs can test billions per second, so this falls in days to weeks of offline cracking. Each additional character multiplies the time by the character set size.

Dictionary attacks try words from a dictionary, common passwords, and their mutations (capitalizing, appending digits, leet substitutions). The RockYou breach leaked 14 million passwords, which became a standard wordlist. Any password in that list is cracked instantly. Rainbow tables are precomputed tables of password hashes, but they are defeated by proper salting.

Credential stuffing takes username-password pairs leaked from one breach and tries them on other services, exploiting password reuse. This is why unique passwords per account are non-negotiable. Phishing tricks users into entering passwords on fake sites, bypassing all cryptographic strength; this is why MFA and passkeys matter even with strong passwords.

// Estimating crack time against offline attack
// Assuming 10 billion guesses/sec (commodity GPU farm in 2024)

function estimateCrackTime(entropyBits) {
  const guessesPerSecond = 1e10;  // 10 billion/sec
  const halfSpace = Math.pow(2, entropyBits - 1);  // Average: half the keyspace
  const seconds = halfSpace / guessesPerSecond;

  if (seconds < 1) return 'Instant';
  if (seconds < 60) return Math.round(seconds) + ' seconds';
  if (seconds < 3600) return Math.round(seconds / 60) + ' minutes';
  if (seconds < 86400) return Math.round(seconds / 3600) + ' hours';
  if (seconds < 31536000) return Math.round(seconds / 86400) + ' days';
  if (seconds < 31536000 * 100) return Math.round(seconds / 31536000) + ' years';
  if (seconds < 31536000 * 1e9) return Math.round(seconds / 31536000 / 1e6) + ' million years';
  return 'Effectively uncrackable';
}

console.log(estimateCrackTime(28));  // Instant
console.log(estimateCrackTime(40));  // 18 hours
console.log(estimateCrackTime(56));  // 2 years
console.log(estimateCrackTime(80));  // 19 million years

The crack time estimates above assume offline attacks against hashed passwords, which is the worst-case scenario. Online attacks against a live login form are far slower because of network latency and rate limiting. The distinction matters for security planning: a 40-bit password might survive an online attack (rate-limited to perhaps 100 guesses per second) for years, but fall to an offline attack in hours. This is why protecting the password hash database is as critical as the password strength itself. If hashes never leak, even moderate passwords are safe; if they do, only high-entropy passwords survive.

Generating Cryptographically Secure Passwords

The single most important rule of password generation: use a Cryptographically Secure Pseudo-Random Number Generator (CSPRNG). In JavaScript, Math.random() is NOT a CSPRNG; it uses a predictable algorithm seeded from the system clock, making its output guessable to an attacker who can approximate the generation time. Never use it for security-sensitive randomness.

In the browser, use the Web Crypto API's crypto.getRandomValues(). In Node.js, use crypto.randomBytes(). Both draw from the operating system's cryptographically secure entropy source, which collects environmental noise (hardware events, timing jitter) to produce output that is practically impossible to predict.

// CORRECT: Cryptographically secure password generation
function generateSecurePassword(length = 16) {
  const charset = 'abcdefghijklmnopqrstuvwxyz' +
                  'ABCDEFGHIJKLMNOPQRSTUVWXYZ' +
                  '0123456789' +
                  '!@#$%^&*()_+-=[]{}|;:,.<>?';
  const array = new Uint32Array(length);
  crypto.getRandomValues(array);  // CSPRNG — Web Crypto API

  let password = '';
  for (let i = 0; i < length; i++) {
    // Use modulo with rejection sampling to avoid modulo bias
    const index = array[i] % charset.length;
    password += charset[index];
  }
  return password;
}

// WRONG: Math.random() is NOT cryptographically secure
function insecurePassword(length) {
  const charset = 'abcdef...';
  let pw = '';
  for (let i = 0; i < length; i++) {
    pw += charset[Math.floor(Math.random() * charset.length)]; // PREDICTABLE
  }
  return pw;
}

// Correct modulo to eliminate bias (for critical applications):
function unbiasedRandomInt(max, randomValue) {
  // Reject values that would create modulo bias
  const limit = Math.floor((0xFFFFFFFF + 1) / max) * max;
  if (randomValue >= limit) return null;  // Re-roll
  return randomValue % max;
}

console.log(generateSecurePassword(20));
// Output: e.g. "Km7#vQ2$pL9!nX4@rB3^"

For modulo bias: when you take randomValue % charsetLength, if the random range is not evenly divisible by the charset length, some characters appear slightly more often, reducing effective entropy. For most applications this bias is negligible, but for high-security systems, use rejection sampling as shown. Our password generator tool uses crypto.getRandomValues() with proper bias handling.

Password Storage Best Practices

Never store passwords in plaintext. If your database is compromised, every plaintext password is immediately usable. The correct approach is to hash passwords with a slow, salted key derivation function. Hashing is one-way: you can compute the hash from the password, but you cannot recover the password from the hash. When a user logs in, you hash their input and compare it to the stored hash.

bcrypt and Argon2 are the standard algorithms. Unlike fast hashes like SHA-256, which are designed for speed, these are deliberately slow and memory-hard. bcrypt has a configurable cost factor; Argon2 adds memory hardness to resist GPU and ASIC attacks. A salt, unique per password, is stored alongside the hash and prevents rainbow table attacks: two users with the same password get different hashes.

// Node.js — Password hashing with bcrypt
const bcrypt = require('bcrypt');

async function hashPassword(plaintext) {
  // Cost factor 12 = 2^12 = 4096 rounds. Adjust based on hardware.
  // Target: ~250ms per hash on your production server.
  const saltRounds = 12;
  const hash = await bcrypt.hash(plaintext, saltRounds);
  // Hash includes the salt and cost: $2b$12$
  return hash;
}

async function verifyPassword(plaintext, storedHash) {
  return await bcrypt.compare(plaintext, storedHash);
}

// Argon2 (modern recommendation, OWASP preferred)
const argon2 = require('argon2');

async function hashPasswordArgon2(plaintext) {
  const hash = await argon2.hash(plaintext, {
    type: argon2.argon2id,        // Hybrid: resists both side-channel and GPU attacks
    memoryCost: 19456,             // 19 MB — memory-hard
    timeCost: 2,                   // 2 iterations
    parallelism: 1
  });
  return hash;
}

// NEVER do this — SHA-256 is too fast for password storage
const crypto = require('crypto');
function insecureHash(password) {
  return crypto.createHash('sha256').update(password).digest('hex');
  // An attacker with the hash can try billions of guesses per second
}

A pepper is a server-side secret added to each password before hashing. Unlike the salt, the pepper is not stored in the database; it lives in application configuration or a hardware security module. If only the database is stolen, the hashes remain uncrackable even with weak passwords, because the attacker does not have the pepper. This adds defense-in-depth against database-only breaches.

Password Managers and Policies

NIST Special Publication 800-63B (2017 revision) fundamentally changed password policy guidance. The key recommendations: require a minimum length of 8 characters (16+ preferred), screen new passwords against known breached password lists, allow long passwords (up to 64+ characters) to encourage passphrases, and do not require composition rules or mandatory periodic resets unless compromise is suspected. Forced periodic resets lead users to create predictable patterns (Password1, Password2, ...) that reduce security.

Password managers solve the human limitation of memorizing unique high-entropy passwords. A single strong master password protects an encrypted vault of generated passwords. Recommend or require password manager use, and support autofill so users are not tempted to reuse passwords across sites. Multi-factor authentication (MFA) adds a second factor, so a stolen password alone is insufficient. Passkeys (WebAuthn / FIDO2) are replacing passwords entirely: they use public-key cryptography with device-based authentication, are phishing-resistant by design, and eliminate the need for users to create or remember passwords. Where passkeys are available, they are strictly more secure than passwords.

The migration path from passwords to passkeys is gradual. Most systems will support both during a transition period, and some accounts may require password fallback for recovery. When implementing passkeys, use the WebAuthn API with a relying party identifier tied to your domain. The public key is registered server-side, and the private key never leaves the user's device, making server-side breaches far less damaging. For organizations, enforce passkey enrollment through policy and provide clear user education, because the mental model of device-based authentication differs from the password habits users have built over decades. The investment in transition pays off in reduced support costs, eliminated password reset tickets, and closure of the phishing vector that passwords always leave open.

Frequently Asked Questions

How long should my password be?

Aim for at least 16 characters for important accounts. A 16-character password with a full character set provides over 100 bits of entropy, which is computationally infeasible to crack. If you use a password manager, 20+ characters costs you nothing and adds a large margin of safety.

Is a long password better than a complex one?

Length generally beats complexity because each character multiplies the search space. A 20-character lowercase passphrase has more entropy than an 8-character password with symbols. NIST now recommends prioritizing length over mandatory composition rules.

What is password entropy?

Entropy measures password unpredictability in bits, calculated as length times the base-2 logarithm of the character set size. Higher entropy means more possible combinations an attacker must try. A 60-bit password is considered reasonable; 128 bits is cryptographically strong.

Are password managers safe?

Yes, password managers are safer than the alternatives. They generate unique high-entropy passwords for every account and encrypt them with a single master password. The main risk is the master password, so use a long passphrase and enable MFA on the vault.

What is a passkey?

A passkey is a replacement for passwords based on public-key cryptography. Your device stores a private key and registers a public key with the service. Passkeys are phishing-resistant, require no memorization, and use device authentication like fingerprint or face unlock. They are the strongest consumer authentication method available today.
