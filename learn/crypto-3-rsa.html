RSA Encryption: A Practical Developer Guide

RSA is the most widely deployed asymmetric encryption algorithm, securing everything from HTTPS connections to email encryption and software signing. Unlike symmetric encryption where one key does everything, RSA uses a pair of keys: one public, one private. This guide covers the mathematics behind RSA, how key generation works, what digital signatures are, and how to implement RSA correctly in real applications. Understanding RSA is essential for any developer working with authentication, TLS, or secure communications.

What is RSA Encryption?

RSA is an asymmetric (public-key) cryptosystem invented by Ron Rivest, Adi Shamir, and Leonard Adleman in 1977 (the name RSA comes from their initials). Asymmetric cryptography uses two mathematically related keys: a public key that can be freely shared and a private key that must be kept secret. Data encrypted with the public key can only be decrypted with the corresponding private key, and vice versa.

This property solves the key distribution problem that plagues symmetric encryption. With AES, both parties must share a secret key over a secure channel before communicating. With RSA, anyone can encrypt a message using the recipient's public key, but only the recipient can decrypt it with their private key. No secure key exchange is needed beforehand.

The security of RSA rests on the practical difficulty of factoring the product of two large prime numbers. Given the product of two large primes (called the modulus), recovering the individual primes is computationally infeasible with current technology. This is the one-way function that makes RSA secure: multiplying two primes is easy, but factoring the result back into primes is hard. The RSA name for this is the integer factorization problem.

How RSA Works Mathematically

RSA key generation starts by selecting two large prime numbers, p and q. These should be roughly equal in length and randomly chosen. Their product n = p x q is the modulus, which is part of both the public and private keys. The modulus size (e.g., 2048 or 4096 bits) determines the key size.

Next, compute Euler's totient function: phi(n) = (p-1)(q-1). This value is used to determine the public and private exponents. Choose a public exponent e that is coprime to phi(n). The number 65537 (2^16 + 1) is the standard choice for e because it is prime, large enough for security, and has a simple binary form that makes exponentiation efficient.

Compute the private exponent d as the modular multiplicative inverse of e modulo phi(n), meaning d x e = 1 (mod phi(n)). The public key is the pair (n, e) and the private key is (n, d). The primes p and q are no longer needed and should be destroyed to prevent compromise if they are leaked.

Encryption works by raising the plaintext (as a number) to the power e modulo n: ciphertext = plaintext^e mod n. Decryption raises the ciphertext to the power d modulo n: plaintext = ciphertext^d mod n. This works because of the mathematical relationship between e and d through Euler's theorem. In practice, this raw mathematical operation is wrapped in padding schemes (like OAEP) to prevent a range of attacks that would otherwise make RSA insecure.

RSA Signatures and Verification

RSA's dual-key property enables digital signatures. The private key can be used to sign a message, and the public key can be used to verify the signature. This is the reverse of encryption, where the public key encrypts and the private key decrypts.

To sign a message, the sender hashes the message and encrypts the hash with their private key. The recipient decrypts the signature using the sender's public key, hashes the message independently, and compares the two hashes. If they match, the recipient knows the message was not tampered with (integrity) and that it came from the holder of the private key (authenticity).

Digital signatures provide non-repudiation, meaning the signer cannot later deny having signed the message, because only they possess the private key. This is a property that symmetric-key authentication (like HMAC) cannot provide, since both parties share the same key. RSA signatures are used in code signing (verifying software authenticity), certificate authorities (signing TLS certificates), and document signing (PDF signatures, legal contracts).

RSA in Practice

RSA has practical limitations that make it unsuitable for encrypting large amounts of data directly. The plaintext that RSA can encrypt is limited by the key size: with a 2048-bit key, you can encrypt at most 245 bytes of plaintext (after OAEP padding overhead). RSA is also computationally expensive compared to symmetric encryption, being roughly 1000 times slower than AES.

The solution is hybrid encryption. The sender generates a random AES key, encrypts the data with AES, and encrypts the AES key with the recipient's RSA public key. The recipient decrypts the AES key with their RSA private key, then uses it to decrypt the data. This combines RSA's key distribution advantage with AES's speed. This is exactly how TLS, PGP, and most secure messaging systems work.

Key size matters. 1024-bit RSA keys are no longer considered secure and have been broken by researchers. 2048-bit keys are the current minimum standard and are expected to remain secure until at least 2030. 4096-bit keys provide additional margin for long-term protection. NIST recommends transitioning to 3072-bit or larger keys for data that needs protection beyond 2030. For quantum-resistant cryptography, RSA will eventually need to be replaced by post-quantum algorithms, but that transition is still in its early stages.

Implementing RSA

The browser's Web Crypto API supports RSA-OAEP for encryption and RSA-PSS for signatures. Key generation, encryption, and decryption are all available natively:

// Generate RSA key pair (2048-bit)
const keyPair = await crypto.subtle.generateKey(
  {
    name: "RSA-OAEP",
    modulusLength: 2048,
    publicExponent: new Uint8Array([1, 0, 1]), // 65537
    hash: "SHA-256"
  },
  true,
  ["encrypt", "decrypt"]
);

// Encrypt with public key
const ciphertext = await crypto.subtle.encrypt(
  { name: "RSA-OAEP" },
  keyPair.publicKey,
  new TextEncoder().encode("Secret message")
);

// Decrypt with private key
const plaintext = await crypto.subtle.decrypt(
  { name: "RSA-OAEP" },
  keyPair.privateKey,
  ciphertext
);

In Python, the cryptography library provides a high-level interface for RSA operations. The library handles padding, key serialization, and key parsing. Always use OAEP padding for encryption and PSS padding for signatures. Never use raw RSA (no padding), which is vulnerable to numerous attacks.

from cryptography.hazmat.primitives.asymmetric import rsa, padding
from cryptography.hazmat.primitives import hashes

# Generate key pair
private_key = rsa.generate_private_key(
    public_exponent=65537,
    key_size=2048
)
public_key = private_key.public_key()

# Encrypt with public key
ciphertext = public_key.encrypt(
    b"Secret message",
    padding.OAEP(
        mgf=padding.MGF1(algorithm=hashes.SHA256()),
        algorithm=hashes.SHA256(),
        label=None
    )
)

# Decrypt with private key
plaintext = private_key.decrypt(
    ciphertext,
    padding.OAEP(
        mgf=padding.MGF1(algorithm=hashes.SHA256()),
        algorithm=hashes.SHA256(),
        label=None
    )
)

Common RSA Security Issues

Using small public exponents like e=3 creates vulnerabilities where an attacker can recover plaintext from ciphertext without factoring the modulus. The standard exponent 65537 avoids this problem while remaining efficient. Never change the public exponent to a small value for performance reasons.

Failing to use proper padding is the most dangerous RSA mistake. Raw RSA (also called textbook RSA) is deterministic: the same plaintext always produces the same ciphertext, which leaks information. It is also vulnerable to chosen-ciphertext attacks where an attacker can derive plaintext by modifying the ciphertext and observing the decryption behavior. OAEP (Optimal Asymmetric Encryption Padding) and PSS (Probabilistic Signature Scheme) add randomness and structure that prevent these attacks. Always use OAEP for encryption and PSS for signatures.

Key size is critical. 1024-bit keys have been factored by researchers and should never be used. The minimum acceptable key size is 2048 bits. Keys used for long-term protection or high-value targets should be 3072 or 4096 bits. Key management is equally important: the private key must be stored securely, ideally in a hardware security module (HSM) or a key vault service. If the private key is compromised, all data encrypted with the corresponding public key is compromised.

RSA Key Formats and Serialization

RSA keys can be serialized in several formats, and understanding them is necessary for interoperability between systems. The most common format is PEM (Privacy-Enhanced Mail), which wraps Base64-encoded DER (Distinguished Encoding Rules) data in header and footer lines: -----BEGIN RSA PRIVATE KEY----- and -----END RSA PRIVATE KEY-----.

There are two primary PEM formats for private keys. The traditional PKCS#1 format uses the header -----BEGIN RSA PRIVATE KEY----- and contains only the RSA-specific parameters (modulus, exponents, primes). The newer PKCS#8 format uses -----BEGIN PRIVATE KEY----- and wraps the key in an algorithm identifier envelope, making it format-agnostic. Most modern systems prefer PKCS#8 because it can handle multiple key types.

Public keys have similar format options. The traditional format uses -----BEGIN RSA PUBLIC KEY----- (PKCS#1). The standard format for X.509 certificates uses -----BEGIN PUBLIC KEY----- (SubjectPublicKeyInfo), which wraps the public key with an algorithm identifier. The Web Crypto API exports keys in JWK (JSON Web Key) format, which represents key parameters as Base64URL-encoded JSON, making them easy to use in web applications without parsing binary data.

When working with keys across languages, the cryptography library in Python provides methods to load and dump keys in all common formats. The load_pem_private_key() and load_pem_public_key() functions accept password-protected encrypted private keys. The OpenSSH format, used by ssh-keygen, is another variant that stores keys with a different comment and encoding structure. Always specify the exact format your system expects to avoid compatibility issues.

Frequently Asked Questions

What's the difference between RSA and AES?

RSA is asymmetric (two keys: public and private) and is used for key exchange and signatures. AES is symmetric (one key for both encryption and decryption) and is used for bulk data encryption. RSA is slow and limited in message size; AES is fast and handles arbitrary data sizes. Systems typically use RSA to exchange an AES key, then AES for the actual data.

How big should my RSA key be?

2048 bits is the current minimum standard and is expected to remain secure until at least 2030. Use 3072 or 4096 bits for data requiring long-term protection. 1024-bit keys are insecure and should never be used. The key size determines the maximum plaintext size you can encrypt.

Can I encrypt large files with RSA?

Not directly. RSA can only encrypt data smaller than the key size minus padding overhead (about 245 bytes for a 2048-bit key with OAEP). For large files, generate a random AES key, encrypt the file with AES, and encrypt the AES key with RSA. This is the standard hybrid encryption approach.

What is a digital signature?

A digital signature is created by encrypting a hash of a message with the sender's private key. The recipient verifies the signature by decrypting it with the sender's public key and comparing the result to their own hash of the message. It proves the message came from the sender (authenticity) and was not modified (integrity).

How does RSA work in HTTPS?

During the TLS handshake, the server sends its RSA public key (via its certificate). The client uses RSA to encrypt a pre-master secret and sends it to the server. Both sides derive session keys from the pre-master secret and switch to AES for bulk encryption. RSA solves the key exchange problem; AES handles the actual data encryption.
